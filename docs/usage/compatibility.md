# 与芋道 Cloud、Java 和 Vben 的兼容范围

项目的目标是在[芋道 Cloud 后端](https://github.com/YunaiV/yudao-cloud)中让 **Go 承接 `system`、`infra` 等基础服务，Java 继续提供业务服务**，形成可按基础服务受控切换的异构系统。切换要求共享数据、缓存、令牌和 RPC 契约兼容，并在异常时回切。当前使用固定版本的 `yudao-cloud-mini` system、infra 和管理端做对照；[细分功能与路由矩阵](capability-comparison.md)列出了已有进展。

| 对象 | 固定版本 | 用途 |
| --- | --- | --- |
| `yudao-cloud-mini` | `712fc7c2528e434217833bf04e438bf18a9c96e4`，v2026.08/JDK 25 | Java 运行行为、SQL、路由、RPC |
| `ui/yudao-ui-admin-vben/` 子模块 | `486870dd8496d94b79aaa183069df8407de8cbf9`，v2026.08 | 浏览器联调与 E2E；[本机启动](frontend.md) |
| 本仓库 | 以实际 Git commit 为准 | Go 候选实现 |

上游文档帮助理解功能，但有分歧时，以这些固定源码和真实运行结果为准。商城、工作流、支付等完整 Cloud 的业务模块继续由 Java 承担，不计算为本项目的 Go 重写缺口；它们与 Go 基础服务的调用兼容性仍须验证。固定 Mini 根 POM 并未启用这些业务模块，目标环境实际启用清单需要单独核实。

## 当前判断

这个目标分成三道门：**能共存**（Java/Go 进程与依赖可同时工作）、**能切换**（路由、流量与行为经过对照）、**能回滚**（流量回切后数据和缓存仍一致）。`cmd/system`、`cmd/infra` 和现有 Gateway/Nacos 提供了拆分部署入口，但入口存在不等于动态替换机制与验收已经完成。

代码已经包含单进程和拆分入口，并在登录、权限、租户、消息、文件、配置、代码生成等基础能力上落地了大量实现。按 2026-09-25 的静态盘点，Go 的 Controller 路径为 **313/314**（system 212/212、infra 101/102），Feign 为 **62/62**（system 56/56、infra 6/6）。唯一未按字面命中的文件下载路径采用不同框架的通配符语法，需运行时验证。路径命中不说明字段、数据权限、错误码和副作用一致；详情和逐功能计数见[能力对照](capability-comparison.md)。

至少还要证明：

- 所有启用的管理接口和 Feign/RPC 的请求、响应、权限、租户、事务与错误行为和 Java 对齐；代码生成等复杂功能要看生成物。
- Vben 在真实浏览器中完成关键路径和失败路径，不能只靠前端构建。
- Java/Go 混跑时共享令牌、角色/部门缓存、删除和并发写入不会产生权限漂移。
- 生产密钥、Nacos/网关、数据库备份、观测、限流与回滚方案都在目标环境演练。

所以当前结论是**可用于本机开发与隔离环境联调，尚不能替换线上 Java 服务**。开源仓库的发布版本和生产替换验收应分开命名；实现功能时把新增证据写进 PR 和相关文档，维护者再归档到重写工作区中与本仓库同级的 `docs/iterations/`。路由数量接近不能改变验收结论。

更完整的审查记录保留在重写工作区的项目级 `docs`；那些记录也不是本仓库的发布证明。
